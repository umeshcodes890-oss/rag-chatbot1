1 · What RAG is and why core idea

RAG = Retrieval-Augmented Generation: look up facts first, then let the LLM answer from what you found.

A plain LLM (like Gemini) only knows what it memorized during training. Ask it about your company's lease contract and it either says "I don't know" — or worse, invents a confident answer (a hallucination).

Retrieval-Augmented Generation fixes this with two steps:

Your documents
→
Chopped into chunks
→
Stored as vectors
→
Question arrives
→
Find top-3 similar chunks
→
LLM answers
using ONLY those chunks
Analogy: an open-book exam. A raw LLM is a student answering from memory. RAG lets the student first find the relevant pages in the book (retrieval), then write the answer copying evidence from those pages (generation). If the pages don't contain the answer, the honest student says so.

The three letters

LetterMeansIn this project
RetrievalFind similar text chunksretrieval.py + ChromaDB
AugmentedPaste findings into the promptgrounded prompt in retrieval.py
GenerationLLM writes the final answerGemini via llm.py

2 · Project architecture: one seam per stage implemented

Each file does exactly one job; only pipeline.py knows the whole order.

Think like a Java developer: this repo is interfaces everywhere, implementations later. Every stage depends only on config.Settings and LlamaIndex types — never on another stage. That means you can test or replace any module in isolation (like swapping one class behind a Java interface).

rag_chatbot/
├── ingestion.py     files → Documents            ✅ implemented
├── chunking.py      Documents → TextNodes        ✅ implemented
├── embeddings.py    build local embed model      ✅ implemented
├── vector_store.py  persist chunks (ChromaDB)    ⬜ stub
├── llm.py           build Gemini chat model       ⬜ stub
├── retrieval.py     find chunks → cited Answer    ⬜ stub
├── chatbot.py       conversation state            ⬜ stub
└── pipeline.py      wires everything together     ⬜ stub

From pipeline.py's own docstring:

"""Pipeline orchestration: wire the stages together in dependency order.

The only module that knows the whole flow. UI code and tests call these functions
rather than sequencing ingestion, chunking, embeddings, and storage themselves —
which is what keeps `app` free of pipeline logic."""
Analogy: a restaurant kitchen. Each cook (module) handles one station — chopping, grilling, plating. The head chef (pipeline.py) alone decides the order of steps. The waiter (app.py) only talks to the head chef, never to the cooks.
Why does this matter? (the "seam" idea)

A seam is a place where you can change behavior without changing the caller. llm.py is described as the "single seam between the rest of the codebase and the Google provider SDK" — if you ever swap Gemini for another model, only that one file changes. This is the same reasoning as depending on a Java interface instead of a concrete SDK class.

3 · Ingestion: files → Documents implemented

Find the supported files, read each format, clean the text — without ever changing a word.

What counts as a document?

SUPPORTED_EXTENSIONS: Final[tuple[str, ...]] = (".pdf", ".docx", ".txt", ".md")

discover_files() scans data/ recursively (subfolders included). Unknown types raise UnsupportedFileError; an absent folder raises FileNotFoundError.

Per-format readers

FormatReaderResult
.pdfLlamaIndex PDFReader (uses pypdf)one Document per page → pages keep page_number
.docxDocxReader (uses docx2txt)whole body as one Document (no page info — docx2txt discards pagination)
.txt / .mddirect readUTF-8, falling back to latin-1

Cleaning that never rewrites content

clean_text() fixes layout noise from extraction but never touches wording: \r\n → \n, non-breaking spaces → normal spaces, zero-width characters removed, space/tab runs collapsed, 3+ blank lines → one paragraph break.

# rag_chatbot/ingestion.py — the ordered rules
1. "\r\n" and "\r" become "\n".
2. Non-breaking spaces become ordinary spaces; zero-width characters vanish.
3. Runs of tabs and spaces inside a line collapse to one space.
4. Trailing whitespace is stripped from every line.
5. Three or more consecutive newlines collapse to a single blank line...
6. Leading and trailing whitespace is trimmed from the result.

Bad files don't sink the ship

  • Empty-after-cleaning file → contributes zero documents, no error.
  • Damaged file → CorruptDocumentError; unreadable PDFs can be skipped with load_documents(..., continue_on_error=True) so one bad file cannot discard a whole knowledge base.
Analogy: ingestion is the librarian who takes your messy printouts, photocopies each page, straightens the stapled corners — but never edits a single word, because the words are evidence.

4 · Chunking: Documents → TextNodes implemented

Cut documents into ~512-token pieces along sentence boundaries, with 50 tokens of overlap.

Why chunk at all?

Two reasons: (1) a whole 300-page PDF doesn't fit a prompt and dilutes similarity search; (2) retrieval works best when the stored unit is roughly the size of a useful answer — a paragraph, not a book.

The real code

# rag_chatbot/chunking.py
return SentenceSplitter(
    chunk_size=chunk_size,        # default 512 tokens
    chunk_overlap=chunk_overlap,  # default 50 tokens
    include_metadata=True,
)

Reading the geometry

chunk 1: tokens 0–511
⟲
chunk 2: tokens 462–973
(last 50 shared with chunk 1)

SentenceSplitter packs whole sentences up to the budget, so cuts land between sentences — never mid-word. Only a single oversized sentence is split between words. The overlap means a fact sitting right at a boundary appears complete in at least one chunk.

Metadata survives the cut

Every TextNode copies its source document's metadata: file_name, file_path, file_type, file_size_bytes, last_modified, plus page_number / page_count / page_label for PDFs. This is why a chunk retrieved three stages later can still cite "lease.pdf, page 4".

Analogy: cutting a novel into index cards for a search engine. Cards that end mid-sentence are useless — so you cut between sentences, and repeat the last two sentences on the next card so no thought gets lost at a seam.
What is a "token"? (Java devs: not a character)

A token is a piece of word as the model's tokenizer sees it — roughly ¾ of a word for English. 512 tokens ≈ 380 words ≈ one solid paragraph. chunk_overlap ≥ chunk_size is rejected by _validate_geometry() because every chunk would then be pure repetition with no new text.

5 · Embeddings: turning meaning into numbers implemented

A local model maps every chunk to 384 numbers; similar meaning ⇒ nearby numbers.

An embedding model is a neural network that takes text and outputs a fixed-length list of numbers (a vector). The magic: the numbers encode meaning, so

  • "The lease expires in June" and "Rental agreement ends June" → very close vectors,
  • and either of those vs "Bananas are yellow" → far apart.

Now "find text related to the question" is just arithmetic: compare vectors.

The real code

# rag_chatbot/embeddings.py
return HuggingFaceEmbedding(model_name=settings.embedding_model)
# default: "sentence-transformers/all-MiniLM-L6-v2" → 384-dim vectors, runs on YOUR machine

How similarity is measured: cosine

Cosine similarity compares the angle between two vectors, ignoring their length: 1.0 = same direction (near-identical meaning), 0 = unrelated, -1 = opposite. That score is exactly what shows up under "Sources" in the UI.

Why local embeddings matter

  • Privacy: your document text never leaves the machine for embedding — only the small retrieved context is sent to Gemini at question time.
  • Cost: no per-call embedding API fees.
  • One-time download: first run fetches model weights to ~/.cache/huggingface; after that, offline.
  • Build once: loading the model is slow, so app.py caches it via st.cache_resource. If the model fails to load, you get EmbeddingModelError with the original cause chained (raise ... from exc — Python's version of exception chaining, like Java's cause).
Analogy: a map of meaning. Every sentence gets GPS coordinates in 384-dimensional space. "Find related text" becomes "find the nearest coordinates" — a distance lookup, not a keyword match. This is also why searching "car" finds a paragraph that only says "automobile": on the map, they live next door.

6 · Vector store: ChromaDB stubbed — next to implement

A database whose rows are (text + vector), built for "give me the K nearest vectors".

A normal relational DB answers "WHERE name = 'x'". A vector store answers "which 3 stored vectors are closest to this vector?" — a query equality checks can't express. ChromaDB is a lightweight one that persists on disk (here, in vectorstore/), so the index survives restarts — ingest once, ask many times.

What the stub promises

# rag_chatbot/vector_store.py — intended implementation (docstring)
create a chromadb.PersistentClient rooted at settings.chroma_dir,
get or create the settings.chroma_collection collection,
wrap it in llama_index.vector_stores.chroma.ChromaVectorStore.

7 · Retrieval: finding the evidence stubbed

Embed the question, ask Chroma for the top-3 nearest chunks, keep their scores.

The shapes already designed

Even though the logic is stubbed, the value objects exist — read them like Java records:

@dataclass(frozen=True, slots=True)
class Source:              # one cited chunk
    document_name: str     # which file
    score: float | None    # cosine similarity
    text: str              # the chunk, verbatim

@dataclass(frozen=True, slots=True)
class Answer:              # reply + its evidence
    text: str
    sources: tuple[Source, ...]

Top-K

build_retriever(index, top_k=settings.similarity_top_k) — default K=3. Design trade-off you should understand:

  • K too small → the true answer's paragraph never reaches the prompt → "not in context".
  • K too large → prompt bloats, costs rise, and irrelevant chunks invite the model to drift.
Analogy: the reference desk at a library. You hand over your question; the librarian returns the 3 most relevant index cards with a relevance stamp on each. The retrieval module is forbidden from writing anything (the docstring says so) — it only hands cards to the writer.

8 · Grounded generation & citations stubbed

The prompt forces the model to answer only from retrieved context — and name the file it came from.

The system prompt (already written in chatbot.py)

DEFAULT_SYSTEM_PROMPT = (
    "You are a document question-answering assistant. Answer only from the "
    "provided context. If the context does not contain the answer, say so "
    "plainly instead of guessing, and cite the source document."
)

Three rules packed in there, each fighting a specific LLM failure:

  1. "only from the provided context" — blocks using training memory (the hallucination source).
  2. "say so plainly instead of guessing" — makes "I don't know" a valid, non-punished answer.
  3. "cite the source document" — makes every claim checkable against a chunk.

The generator

# rag_chatbot/llm.py — intended (stubbed) implementation
GoogleGenAI(settings.gemini_api_key, model="gemini-2.5-flash", temperature=low)

A low temperature is chosen deliberately: temperature controls randomness. Grounded Q&A wants factual, repeatable output, not creativity.

Analogy: a lawyer's brief. The retrieved chunks are exhibits; the system prompt is the judge instructing "argue only from exhibits on record, cite exhibit numbers, or say you have no evidence."

9 · Streamlit: the UI and its strange state model implemented

The whole script re-runs on every interaction — so state lives in session_state and heavy objects in cache_resource.

Unlike Spring/JavaFX where the app is a running process with event handlers, a Streamlit script executes top-to-bottom again on every click or keystroke. Two tools tame that:

st.session_state — the per-browser-tab dictionary

# app.py — chat history survives reruns
st.session_state.messages.append(
    {"role": "assistant", "content": answer.text, "sources": answer.sources}
)

@st.cache_resource — don't reload the model 50 times

@st.cache_resource(show_spinner="Loading configuration...")
def get_settings() -> Settings:
    return load_settings()

The function runs once per process; later reruns reuse the cached object. Ingesting rebuilds the index, so the app then calls st.cache_resource.clear() — a deliberate cache bust.

Graceful degradation

Because pipeline stages raise NotImplementedError, the UI catches it and shows "The RAG pipeline is scaffolded but not implemented yet" instead of a stack trace. Presentation logic is all that's real in app.py — no pipeline call, no prompt text, no key handling lives there.

10 · Config & secrets: one door, read once implemented

.env → load_settings() → an immutable Settings object; the key never travels further.

# config.py — a frozen dataclass is Python's nearest cousin to an immutable Java record
@dataclass(frozen=True, slots=True)
class Settings:
    gemini_api_key: str      # required
    gemini_model: str = "gemini-2.5-flash"
    embedding_model: str = "sentence-transformers/all-MiniLM-L6-v2"
    chunk_size: int = 512
    chunk_overlap: int = 50
    similarity_top_k: int = 3
    ...

The rules this file enforces

  • Validate at the boundary. Missing GEMINI_API_KEY → ConfigError at start-up, not a cryptic 401 three stages later. CHUNK_OVERLAP ≥ CHUNK_SIZE is also rejected here.
  • Secrets go one way. .env is gitignored; the key is read once and only llm.py ever uses it. UI and storage modules physically cannot see it.
  • Even repr hides it. Printing Settings shows gemini_api_key='***' — so a stray debug print can't leak the key into a log or screenshot.
  • Gated HF models: HuggingFaceEmbedding has no token argument — huggingface_hub reads HF_TOKEN from the environment that load_settings already populated. No plumbing, no passing secrets as parameters.
Analogy: hotel keycards. The front desk (config.py) creates and encodes them once; guests (modules) use them at their own door; nobody writes the master code on paper.

11 · How this project is tested 86 offline tests

Real files instead of mocks; live API calls quarantined from the suite.

  • Real fixtures, no fake I/O: tests/conftest.py generates actual PDF and DOCX files, so pypdf, docx2txt and the LlamaIndex readers are genuinely exercised. (Python's pytest ≈ JUnit; a fixture ≈ a @BeforeEach factory method.)
  • Tested properties, not pixels: chunking tests check geometry, token budgets, overlap, metadata; embedding tests check vector shape, determinism, and semantic ranking ("cat" sentence closer to "kitten" than to "invoice").
  • The live API is excluded on purpose: tests/test_geminiapi.py is a stand-alone connectivity script. pytest never imports it, because its body spends a real (billable) Gemini request at import time. Run it manually: python tests\test_geminiapi.py.
  • Offline by design: the whole 86-test suite runs in ~35s without network (after the one-time model download).
Analogy: testing a toaster by toasting real bread, not by mocking "bread-like objects". But the electricity bill (the paid API) is only tested when you flip that switch yourself.

12 · Roadmap: what's left to implement 4 stubs remain

Build bottom-up: storage → generation → retrieval → wiring → chat.

From the README, in order — now you know what each line actually means:

  1. vector_store.py — persistent Chroma client + VectorStoreIndex (match 384 dims; implement index_exists, reset_index).
  2. llm.py — return a GoogleGenAI model from config; low temperature.
  3. retrieval.py — retriever (top-K=3) + grounded prompt → real Answer/Source objects.
  4. chatbot.py + pipeline.py — history-aware Chatbot.ask(), then wire the whole order in the two pipeline functions. The UI already handles everything they will return.

The mental model to keep: the document pipeline (ch. 3–6) is a write path you run once per change set; the question pipeline (ch. 5, 7–8) is a read path run per message, reusing the same embed model so questions and chunks live in one comparable vector space. Everything else — Streamlit, config, tests — exists to keep those two paths honest, safe, and verifiable.
